# 评委方法论

## 1. 默认赛道

SpeechMirror 面向计算机应用作品类答辩。默认评分不是学术论文答辩，也不是创业计划书评审。系统保留用户材料中的项目事实，再用以下作品赛维度组织训练反馈：

| 维度 | 分值 | AI 训练时的可观察问题 |
|---|---:|---|
| 作品创意与市场前景 | 15 | 要解决的具体问题、目标用户、现有替代方案、创意是否可实现 |
| 功能与 UI 设计描述 | 10 | 功能边界、页面跳转、设计是否与实现一致 |
| 功能实现与作品演示 | 30 | 关键链路是否真的完成、输入输出、异常处理、网络环境和可复现结果 |
| 文档设计 | 20 | 架构、算法、数据流、接口和图文是否互相印证 |
| 现场陈述与回答问题 | 15 | 是否直接回答、能否引用具体实现、能否承认边界并应对追问 |
| 团队合作 | 10 | 分工、贡献、代码/文档/演示的一致性 |

用户提供的作品评分表是正式依据。压缩包中的学术答辩和双创规则只作为方法论补充，不得把“商业价值30分”误套到本项目的作品赛报告。

## 2. 一次提问应该怎样产生

1. 从项目知识库检索与当前陈述相关的材料。
2. 把检索结果拆成完整语义单元，并记录来源文档、页码/段落（后端当前至少记录 chunk_id）。
3. 为每个候选事实标注类型：功能、技术、数据、用户、验证、创新、限制或团队。
4. 对照现场陈述：已覆盖、只说愿景、说法矛盾、完全遗漏、没有验证。
5. 只选择一个缺口提出一个问题，问题中出现项目的专有名词、模块名、数据或条件。
6. 记录 evidence.quote，必须是材料中的连续原文；没有证据就不提项目事实问题。
7. 读取同一项目近期已经使用的问题，拒绝完全相同或高度相似的问法；如果历史问题相似但本次确实核查另一个材料事实，才允许保留。

好的问题示例：

- 材料写明“音频经 HTTPS 临时发送至后端 ASR”。你在断网时如何处理录音和重试，当前演示验证了哪一种失败场景？
- 材料写明“Rust 在单项目范围计算余弦相似度”。为什么没有使用外部向量数据库，项目规模扩大后最先遇到的瓶颈是什么？
- 材料写明“端侧只上传派生视觉指标”。这些指标如何与 iOS、Android、HarmonyOS 保持同一含义，你用什么测试集验证过？

坏的问题示例：

- “请介绍一下你的项目。”
- “你的项目有什么创新？”
- “材料提到‘SpeechMirror iOS VPS 回归测试材料’，请说明它如何实现？”

第三类问题暴露了 chunk 截断和脱离语义，后端已禁止以 chunk 前缀作为 fallback 问题锚点。

## 3. 回答怎样评分

回答评价顺序固定为：

1. **相关性**：是否先回答了当前问题，而不是换题。
2. **要点覆盖**：问题要求的输入/输出、理由、结果、边界或验证，回答覆盖了哪些。
3. **材料一致性**：说法能否在项目知识库中找到连续证据。
4. **真实性**：是否把计划、设想或未完成内容冒充已实现。
5. **应变**：追问时能否承接上一轮缺口，修正、补充或明确不知道。
6. **表达**：结论、依据、边界是否清楚；表达分不能掩盖内容错误。

“说得长”不是高分条件。完全跑题、只讲愿景或无法与材料对应的回答应落入低分段；只有覆盖关键要点并给出可核验实现/结果/限制时，才允许进入较高分段。

## 4. 追问规则

- 首轮回答有关键缺口、矛盾或无依据断言时只追问一次。
- 追问必须承接上一轮具体缺口，不重新问原问题，也不使用“请结合材料补充……”万能句。
- 第二轮回答结束后不再自动生成 follow_up。
- 如果回答已经明确承认材料未提供证据，评委应要求其区分“已实现”“计划”“未验证”，而不是继续逼问不存在的数据。
